Overview

Brainchild is a low-level, VM-targeted programming language designed around explicit control, predictable costs, and user-defined abstractions. The language intentionally avoids hidden runtime behavior such as garbage collection, implicit ownership, or enforced type hierarchies.

Brainchild code is compiled to a compact assembly language executed by a minimal virtual machine. The VM provides only integer registers, stacks, and a word-addressed heap. All higher-level constructs are expressed through libraries, macros, and disciplined usage patterns.

Key design principles:

  • No garbage collection; all memory management is explicit or scoped.

  • No runtime type enforcement beyond what the user and compiler provide.

  • Predictable execution and allocation costs.

  • Abstractions are library-defined, not built into the runtime.

  • Explicit mutation and ownership are preferred over implicit copying.

Brainchild is intended for systems programming, tooling, terminal applications, and experimentation with language and VM design.

Non-Goals

The following are explicitly not goals of the language:

  • Automatic memory management.

  • Implicit reference counting or garbage collection.

  • Strong runtime type safety.

  • High-level object lifetimes enforced by the compiler.

Where safety exists, it exists by convention, explicit structure, and careful API design.

Comments

Brainchild supports both line comments and block comments.

Line Comments

Line comments begin with // and extend to the end of the line.

// This is a line comment
    int x = 5; // This comment follows code

Block Comments

Block comments begin with /* and end with */. They may span multiple lines and may also appear inline.

/*
    This is a block comment.
    It may span multiple lines.
    */

    function example(){
        int x = 10; /* Inline block comment */
        x = x + 1;
    }

Block comments are ignored by the compiler. Nesting of block comments is not guaranteed to be supported and should not be relied upon.

Comment Usage Guidelines

  • Use line comments for short, local explanations.

  • Use block comments for file headers, large explanations, or temporarily disabling regions of code.

  • Avoid relying on comment nesting.

Comments have no semantic effect and do not influence compilation, allocation, or runtime behavior.

Virtual Machine

This chapter describes the Brainchild Virtual Machine (VM) and its instruction set. This chapter is specification-level; the VM described here is authoritative.

Machine Model

The Brainchild VM is a simple stack-and-register machine operating on 32-bit integers.

The VM provides:

  • Two general-purpose registers: A and B

  • Two stacks: X and Y, each storing 32-bit integers

  • A word-addressed heap storing 32-bit integers

  • A byte-addressed instruction pointer (IP)

The distinction between word-addressed heap memory and byte-addressed instructions has no impact on observable program semantics.

Stacks and Calling Convention

The two stacks have distinct roles by convention:

  • X stack:

    • Function arguments

    • Return values

    • Temporary evaluation values

  • Y stack:

    • Return addresses for function calls

    • Call-frame metadata

    • Recursion-related state

Function calls push the return address onto the Y stack. Arguments are expected to be pushed onto the X stack by the caller. Return values are left on the X stack by the callee.

Registers

Registers A and B hold signed or unsigned 32-bit values, depending on how the program interprets them. The VM itself does not distinguish signedness.

Many instructions destructively update registers. While this matters at the assembly level, Brainchild language semantics generally abstract this away.

Heap Allocation Primitives

The VM provides built-in alloc and free routines implemented entirely in assembly. These manage the heap as a word-addressed allocation table.

The allocator and deallocator are deterministic and explicit; no garbage collection or background memory management exists.

While the allocator implementation is complex, its observable behavior is: allocate contiguous words, return a pointer, and require explicit freeing.

Syntax and Core Language

This chapter describes the surface syntax of Brainchild and the core language constructs. This chapter is specification-level unless otherwise stated.

Compilation Units and Inclusion

Brainchild source files are plain text. There is no module system beyond textual inclusion.

include file.bc;
Compile-time inclusion
Includes the contents of file.bc at compile time. Inclusion is purely textual; name resolution and ordering are the responsibility of the user.

Multiple inclusion of the same file is permitted and not automatically guarded against.

Statements and Expressions

Brainchild is expression-oriented but distinguishes between statements and expressions syntactically.

Statements include:

  • Variable declarations

  • Assignments

  • Control flow constructs

  • Function and class definitions

Expressions include:

  • Literals

  • Variable references

  • Arithmetic and logical operations

  • Function calls

  • Cast expressions

Semicolons terminate statements. Blocks are delimited by braces.

Variables and Declarations

Variables are declared using a type name followed by an identifier.

int x = 5;
    string s;

The keyword var may be used to allow type inference where the compiler can determine the type unambiguously.

var x = 10;

Assignment

Assignment uses the = operator.

x = x + 1;

Compound assignment operators are provided via macros (see Chapter [chap:macros]) and expand into the corresponding binary operation followed by assignment.

Control Flow

if and else

Conditional execution uses if and else if chains.

if(x > 10)
        y = 1;
    else if(x > 5)
        y = 2;
    else
        y = 3;

The form ; else is forbidden. The else keyword must attach directly to the preceding if or else if block.

while

Loops are formed using while.

while(x){
        x = x - 1;
    }

There is no break statement. Loop termination must be expressed through the loop condition or auxiliary flags.

Functions

Functions are declared using the function keyword.

function add(int a, int b) -> int {
        return a + b;
    }

Functions may omit an explicit return type when returning no value.

Arguments are passed by value at the language level. Underlying calling conventions are handled by the compiler and VM.

Classes and Structs

Structs

Structs are simple aggregate types with named fields.

struct pair<A,B> {
        A a;
        B b;
    }

Structs do not imply ownership or lifetime management.

Classes

Classes support methods, constructors, and virtual dispatch.

class Point {
        int x;
        int y;

        new(int x, int y){
            this.x = x;
            this.y = y;
        }
    }

Classes do not imply automatic allocation. Allocation behavior depends on how instances are created.

Methods and this

Methods receive an implicit this parameter referring to the instance.

class Counter {
        int value;

        function inc(){
            this.value = this.value + 1;
        }
    }

Abstract Classes

Abstract classes may not be instantiated directly and are commonly used as interfaces or method extension points.

abstract class Shape {
        virtual function area() -> int;
    }

Metamethods

Metamethods define operator behavior, implicit casts, indexing, and other language extensions.

metamethod add(int a, int b) -> int {
        return a + b;
    }

Metamethod resolution occurs at compile time. Ambiguous implicit casts are compile-time errors.

Casting

Implicit Casts

Implicit casts are defined via metamethod cast. If more than one valid cast exists, the program is ill-formed.

Explicit Casts

Explicit casts use the -> operator.

int x = (someValue -> int);

The -> operator performs a strict reinterpret cast. Multiple target types may be specified.

(a, b -> int, @int)

Indexing and Pointer Access

Indexing is implemented through metamethods.

  • getindex for reads

  • setindex for writes

  • ptrindex for address access

The ptrindex form corresponds to address-of semantics.

Pointer dereference and address manipulation are explicit and visible at the language level.

Memory and Lifetime

This chapter defines Brainchild’s memory model, ownership conventions, and lifetime control mechanisms. This chapter is specification-level unless explicitly stated otherwise.

Heap Allocation

Brainchild provides explicit heap allocation via the standard library functions alloc and free. The heap is word-addressed and stores 32-bit integers.

alloc(int count)
Heap allocation
Allocates count contiguous 32-bit words on the heap and returns a pointer to the first word. The returned pointer must eventually be freed with free.

free(@int ptr)
Heap deallocation
Releases a heap allocation previously returned by alloc. The pointer must not be used after being freed.

There is no garbage collection. All heap allocations are the programmer’s responsibility.

Stack Allocation and reserve

reserve N
Stack allocation
Reserves N 32-bit integers on the stack. The value of N must be known at compile time.

Stack allocations created by reserve are automatically invalidated when the enclosing scope exits.

Ownership and dispose

Some types define a dispose metamethod. When called, this method releases resources owned by the value.

Calling dispose explicitly is permitted but discouraged except when implementing ownership abstractions.

temp

The temp keyword expresses scoped ownership.

temp expr
Scoped disposal
Evaluates expr and marks the resulting value as owned by the current scope. If the value defines a dispose metamethod, it will be called exactly once when the scope exits, to the extent the compiler can guarantee.

temp var s = stringutils.sub(1, 3, original);
    /* s will be disposed at scope exit */

temp may appear either before a declaration or directly before an expression.

var s = temp stringutils.trim(input);
    temp var t = compute();

defer

The defer keyword schedules an expression to be evaluated at the end of the current scope.

defer expr
Deferred execution
Ensures that expr is executed when the current scope exits, regardless of how the scope is exited.

@int p = alloc(10);
    defer free(p);
    /* p is guaranteed to be freed when scope exits */

Multiple defer expressions execute in reverse order of appearance.

Returning Values Safely

Values marked with temp must not be returned from a function.

function bad() -> string {
        temp var s = stringutils.sub(0, 2, input);
        return s; /* INVALID */
    }

To return a value safely, the returned value must own its storage.

function good() -> string {
        temp var s = stringutils.sub(0, 2, input);
        return stringutils.clone(s);
    }

const

The const keyword forces compile-time evaluation.

const expr
Compile-time evaluation
Evaluates expr at compile time. The result must be representable as a literal in emitted code.

const int

Compile-time integers exist only during compilation and are resolved to literal values in emitted code.

const int letter = 'A';
    letter += 2;
    putchar(letter); /* emits putchar('C') */

const int values may be used with reserve, macros, and other compile-time constructs.

Mutation vs Allocation

Many library functions mutate their arguments rather than allocating new values. This is intentional and should be relied upon for performance.

Examples:

  • string.lower() mutates the string in place.

  • array.modify() mutates array elements.

  • string.sub() allocates a new string.

Each library function documents its allocation and mutation behavior.

While the VM’s arithmetic instructions may be destructive, Brainchild-level arithmetic expressions are safe and do not invalidate operands.

Macros and Compile-Time Facilities

This chapter describes Brainchild’s macro system and compile-time evaluation facilities. This chapter is specification-level unless otherwise noted.

Macro System Overview

Macros in Brainchild operate as syntactic rewrite rules. They are expanded before type checking and semantic analysis.

Macros do not operate on typed ASTs; instead, they match token patterns and produce token sequences.

Defining Macros

Macros are defined using the macro keyword.

macro ( 'for' "(" (expression?) ";" (expression?) ";" (expression?) ")" (expression) ) {
        {
            $1;
            while($2){
                $4;
                $3;
            }
        }
    }

Macro patterns consist of literal tokens and pattern variables. The body of the macro emits replacement tokens.

Macro Expansion Semantics

Macro expansion occurs:

  • Before type checking

  • Before metamethod resolution

  • Before code generation

Macros may expand into arbitrary Brainchild syntax, including blocks, statements, and expressions.

Hygiene and Scope

Macros are not hygienic. Identifiers introduced by macros may collide with names in the surrounding scope.

Macro authors must avoid name collisions manually, typically by choosing unlikely identifier names or using block scoping.

Common Macro Uses

Macros are commonly used to implement:

  • Compound assignment operators

  • Loop constructs

  • Syntactic sugar

  • Compile-time code generation

const and Macros

The const keyword is frequently used within macros to ensure that expressions are evaluated at compile time.

macro ( 'square' (expression) ) {
        const {
            $1 * $1
        }
    }

Compile-Time Arithmetic

const int expressions may perform arithmetic during compilation.

const int size = 4 * 8;
    @int buffer = reserve size;

These values do not exist at runtime.

Limitations

  • Macros cannot inspect types.

  • Macros cannot introduce new scoping rules.

  • Macro expansion errors may be difficult to diagnose.

Macros are powerful but dangerous. Prefer functions and libraries when runtime behavior is sufficient.

Standard Library

This chapter provides a complete, in-depth description of the Brainchild standard library. It is intended as a reference manual, not a tutorial, and documents:

Unless otherwise stated:

  • There is no garbage collection

array.bc

Purpose

array.bc defines the fundamental array abstraction used throughout the standard library. It is intentionally minimal and exposes memory ownership explicitly.

Type: array<T>

An array<T> is a pair of metadata and pointer:

  • count: number of elements

  • data: pointer to contiguous storage

Ownership model:

  • The array may or may not own its backing storage

  • Disposing an array frees data

  • Multiple arrays may alias the same data

Allocation behavior:

  • Construction does not allocate

  • Disposal frees backing memory

Mutation behavior:

  • Indexing mutates underlying memory

Use cases:

  • Passing contiguous memory with explicit length

  • Lightweight views over buffers

  • Interop between libraries

Sharp edges:

  • Disposing one alias invalidates all aliases

  • No bounds checking

arrayutils.bc

Purpose

Provides functional-style operations on array<T>.

Functions

iterate

Semantics: Applies a function to each element. Allocation: None. Mutation: None (unless callback mutates). Use case: Traversal, side-effect processing.

map

Semantics: Produces a new array by transforming each element. Allocation: Allocates new backing storage. Mutation: None to input array. Use case: Structural transformation.

modify

Semantics: Replaces each element with the result of a function. Allocation: None. Mutation: Mutates input array in place. Use case: Efficient bulk mutation.

filter

Semantics: Selects elements based on predicate. Allocation: Allocates new array. Mutation: None. Use case: Selection pipelines. Note: Known bugs in current implementation.

fold

Semantics: Prefix reduction producing intermediate results. Allocation: Allocates array of results. Mutation: None.

reduce

Semantics: Collapses array into single value. Allocation: None. Mutation: None.

Sharp edges:

  • Allocation-heavy if misused

  • Filter correctness depends on version

arraylist.bc

Purpose

Provides a growable, heap-backed array abstraction.

Type: ArrayList<T>

Ownership:

  • Owns backing buffer

Allocation behavior:

  • Allocates on construction

  • Reallocates on growth

Key functions:

Add

Appends an element, reallocating if necessary. Mutation: Yes. Allocation: Possibly.

Iterate

Calls function for each element. Allocation: None.

Shrink

Returns an array<T> containing exactly Size elements. Allocation: Allocates new array buffer.

Sharp edges:

  • Pointers invalidated on growth

  • Disposal not consistently implemented

stack.bc

Purpose

Provides a last-in-first-out container.

Type: Stack<T>

Ownership:

  • Owns backing buffer

Key functions:

Push

Adds element to top. Allocation: Possibly (realloc).

Pop

Removes and returns top element. Allocation: None.

Peek

Returns top element without removing. Allocation: None.

Sharp edges:

  • Disposal not implemented

string.bc

Purpose

Defines the core string representation.

Type: string

Representation:

  • First word: length

  • Following words: characters

Ownership:

  • Strings may be owning or borrowed

  • Disposal frees backing buffer

Mutation:

  • Indexing mutates underlying buffer

Sharp edges:

  • Aliasing can cause surprising mutations

stringutils.bc

Purpose

Provides string manipulation helpers.

Functions

lower, upper, reverse

Mutation: In-place. Allocation: None. Use case: Efficient normalization.

Style Guide

This chapter defines the normative Brainchild style guide. Code adhering to this guide is considered idiomatic Brainchild.

This guide exists to ensure clarity, predictability, and correct ownership handling in the absence of enforced runtime safety.

General Principles

  • Prefer explicitness over convenience.

  • Prefer mutation over allocation.

  • Make ownership visible at the call site.

  • Avoid hidden control flow.

  • Write code that reflects VM cost model awareness.

Memory and Ownership

  • Use temp to express scoped ownership.

  • Never return temp-owned values.

  • Prefer in-place mutation APIs when available.

  • Do not dispose borrowed wrappers.

  • Clearly document whether functions allocate or mutate.

Allocation Discipline

  • Avoid heap allocation in per-frame or tight loops.

  • Hoist allocations out of loops where possible.

  • Prefer reserve for small, fixed-size buffers.

  • Use defer for cleanup when ownership is non-trivial.

Control Flow Style

  • Avoid deeply nested conditionals.

  • Express loop termination via conditions, not flags when possible.

  • Avoid simulating break; restructure loops instead.

  • Keep loops small and explicit.

Functions and APIs

  • Keep functions small and single-purpose.

  • Clearly document ownership of arguments and return values.

  • Avoid APIs that ambiguously allocate or mutate.

Macros

  • Prefer macros only when syntax cannot be expressed as functions.

  • Avoid introducing identifiers into user scopes.

  • Document macro expansion behavior clearly.

Comments and Documentation

  • Use comments to explain why, not what.

  • Prefer line comments for local context.

  • Use block comments for structural documentation.

Formatting

  • Use consistent indentation.

  • Place braces on the same line as declarations.

  • Keep lines reasonably short.

This style guide is normative. Deviations should be justified by measurable performance or clarity benefits.

Sharp Edges

This chapter documents known hazards, surprising behaviors, and intentionally sharp edges of the Brainchild language and standard library. This chapter is informational but essential for correct usage.

Brainchild deliberately exposes low-level behavior. Many errors that would be runtime-checked or prevented in other languages are possible and expected here.

Ownership and Disposal Hazards

  • Disposing a wrapper type (such as array or string) disposes the underlying storage.

  • Multiple wrappers may reference the same storage.

  • Disposing any one of them invalidates all others.

/* Dangerous: disposing a borrowed wrapper */
    array<int> a = getArray();
    array<int> b = a;   // b borrows a's data
    dispose(a);         // b now dangles

Temporary Values

  • Values marked with temp are disposed at scope exit.

  • Returning a temp-owned value is invalid.

  • Passing a temp value to a function that stores it beyond the call is invalid.

Iterator Non-Termination

Many APIs accept iterators that emit values until termination.

  • Iterators have no intrinsic output size.

  • Iterators may run indefinitely.

This commonly occurs with IO-based iterators.

Unsigned Integers and Negative Values

  • All integers are unsigned by default.

  • Negative values rely on two’s complement wrapping.

  • Signed arithmetic is not directly supported.

A signed integer library (sint) is planned but not yet standard.

Arithmetic vs VM Semantics

At the VM level, arithmetic instructions may clear registers as part of their operation. At the Brainchild language level, arithmetic expressions are safe and do not invalidate operands.

Relying on VM-level destruction from Brainchild code is invalid.

Control Flow Limitations

  • There is no break or continue.

  • Loop control must be expressed structurally.

Terminal Rendering

  • Full-screen clears may cause flickering.

  • Prefer delta drawing where possible.

Allocation in Hot Paths

  • Frequent heap allocation can severely degrade performance.

  • Many library functions allocate implicitly.

  • Allocation behavior must be understood and documented.

Macro Hazards

  • Macros are not hygienic.

  • Macros may duplicate expressions with side effects.

  • Errors may appear far from their source.

Sharp edges are not bugs; they are design tradeoffs. Brainchild assumes competent and careful users.

Annotated Examples

This chapter provides complete, idiomatic Brainchild examples with annotations explaining ownership, allocation, mutation, and control-flow choices. These examples are informational but reflect best practice under the normative style guide.

Example: Scoped Allocation and Mutation

include stringutils.bc;
    include io.bc;

    function normalize_and_print(string input){
        /* Allocate a trimmed copy; ownership is scoped */
        temp var trimmed = stringutils.trim(input);

        /* Mutates in place; no allocation */
        trimmed.lower();

        /* Printing does not take ownership */
        print(trimmed);
        /* trimmed is disposed here */
    }

Notes:

  • stringutils.trim allocates a new string.

  • lower() mutates in place.

  • temp ensures disposal at scope exit.

Example: Safe Return of Allocated Data

include stringutils.bc;

    function first_word(string s) -> string {
        /* Allocate substring */
        temp var word = stringutils.sub(0, s.find(' '), s);

        /* Clone to return owned data */
        return stringutils.clone(word);
    }

Notes:

  • Returning a temp-owned value is invalid.

  • Cloning transfers ownership to the caller.

Example: Iterator-Based Formatting

include stringify.bc;
    include io.bc;

    function print_pair(int a, int b){
        printf("($0, $1)", a, b);
    }

Notes:

  • Formatting uses iterators rather than building strings.

  • Output size is not precomputed.

Example: Delta Drawing in Terminal

include term.bc;

    function draw_point(int x, int y, int c){
        Term.Cursor.X = x;
        Term.Cursor.Y = y;
        putchar(c);
    }

Notes:

  • Avoids clearing the screen.

  • Prevents flicker on terminals without VSync.

Example: Loop Without Break

function find_zero(array<int> a) -> int {
        int i = 0;
        int found = 0;
        int result = -1;

        while(i < a.count && !found){
            if(a[i] == 0){
                found = 1;
                result = i;
            }
            i = i + 1;
        }
        return result;
    }

Notes:

  • No break; loop termination is structural.

Example: Deferred Cleanup

include mem.bc;

    function use_buffer(){
        @int buf = alloc(16);
        defer free(buf);

        /* use buf safely */

    } /* buf freed here */

Notes:

  • defer ensures cleanup regardless of exit path.

Module Index

This chapter lists all standard Brainchild modules and summarizes their intended role. Detailed behavior is described in earlier chapters.

  • stringutils.bc String manipulation utilities, including mutation-heavy APIs and allocating transformations.

  • stringify.bc Lazy formatting via iterator-driven emission.

  • extformats.bc Extended formatting for floats, hexadecimal, and binary output.

Numeric Libraries

  • int.bc Integer extensions including exponentiation and emulated bitwise operations.

  • float.bc Software-emulated floating point arithmetic with deterministic behavior.

Input, Output, and Terminal

  • io.bc Character-based input and output utilities.

  • term.bc Terminal control, cursor movement, styling, and event handling.

Miscellaneous

  • mem.bc Memory utility functions such as memcpy and swapping.

  • pair.bc Simple two-value aggregate structure.

  • rand.bc Pseudorandom number generation utilities.

  • extmacros.bc Common macro definitions, including loop constructs and compound assignments.

Known Issues and Notes

Library Bugs and Limitations

The following issues are known and should be accounted for by users:

  • arrayutils.filter contains a known logic bug in some versions and should be used with caution.

  • ArrayList and Stack do not consistently implement disposal across all versions.

  • Some string utilities allocate more aggressively than strictly necessary.

Planned Additions

  • A signed integer library (sint) to provide explicit signed arithmetic semantics.

  • Improved container disposal coverage.

Design Philosophy Reminder

Brainchild intentionally exposes low-level behavior and relies on discipline rather than enforcement. Correctness, performance, and safety are the responsibility of the programmer.
